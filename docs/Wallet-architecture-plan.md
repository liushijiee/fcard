# Fcard 用户钱包与多链架构改造方案

状态：讨论稿 v0.7；日期：2026-10-15。技术约束已补充，业务待定项按第 12 节确认；尚非生产上线批准。

本文件用于讨论和确定钱包改造范围，不表示钱包能力已实现。首页和卡片页已单独进行 UI 调整；钱包、账本和出款服务仍未实施。实施阶段、目录、表名和接口均为建议，讨论后再定稿。

早期变更：已确定采用平台托管钱包，替代 v0.1 中用户与平台共同持有密钥的设计；相应调整密钥管理、授权、余额对账、界面、验收与待讨论事项。

v0.4 补充：测试环境仅使用 Nile，正式环境使用 TRON 主网，通过独立 ENV 文件配置；每用户、每环境独立生成助记词并派生私钥，不使用覆盖全体用户的统一主助记词。

v0.5 补充：根据当前代码和首页、卡片页补充第 14 节评估，包括资金账单、首页读模型、付费开卡资格与名额预留、签名隔离和替换验收。本版不改变已确定的托管模式、独立助记词或 B→C 链上付款规则。

## 1. 目标与已确定的需求

将当前 Epusdt 订单收款模式改为平台托管的用户独立钱包模式：

```text
A：用户外部钱包
       │ 充值
       ▼
B：平台为该用户创建并托管密钥的独立钱包
       ├── 提币 → 用户指定的外部地址
       └── 开卡付款 → C：平台收款钱包
                              │ 确认到账后
                              ▼
                         Fcard 开卡流程
```

已确定：

- 用户建立账号时，为其创建独立钱包；私钥或助记词仅由平台保管，不向用户展示、交付或提供导出。
- 用户通过平台提交提币申请，平台验证和授权后代为签名、广播；开卡付款同样在用户明确确认后，由平台从 B 转账到 C。
- 已付款但开卡失败等异常由人工处理。
- 已确认开卡失败且没有可用卡时，开卡入金全退，已发生服务费按事先约定扣除；结果未知先核查，不立即退款。首期退款由人工授权，执行规则见第 8.4 节。
- 平台先提供 TRX/资源，用户按报价承担链上费用并设实际费用上限；费用扣款币种、换算及结算细则在 P0 定稿，不默认额外补贴或无限扣费。
- 开卡收款包含开卡费、可能的其他费用及开卡入金；开卡入金最低 50 USDT。全部转入平台收款钱包 C，开卡费及其他费用不计入卡额度。
- 不将每笔开卡收款转给 Airwallex；调用其开卡接口，按入金部分对应的 USD 金额设置卡额度。换算规则待定。
- 首期选择 GoTRON SDK 实现 TRON，架构预留其他链。
- 测试环境仅接 Nile，正式环境接 TRON 主网，ENV 配置分开；用户钱包采用各自独立助记词派生私钥，不共用平台统一主助记词。
- 旧方案不再需要的模块和测试数据可以直接清理，不做旧订单兼容或历史支付数据迁移。
- 重视运营成本，第一阶段优先形成 Nile 测试闭环。

本方案属于托管钱包。用户可以查看充值地址、余额和流水，并通过平台申请出款，但不能导入 B 的密钥在外部钱包中自行支出。平台承担密钥保管、备份恢复和受控出款责任；普通管理员不应能够查看明文密钥。平台不可用时，用户无法自行用 B 的密钥提币。

## 2. 当前基础与本次边界

当前项目已有账号权限、用户与管理员会话、Airwallex 沙盒开卡，以及 Epusdt 创建订单和 Fcard 独立验证 TRON 链上支付的能力。已有一次 Nile 测试 USDT 订单确认成功；该确认没有增加用户余额或卡额度。

目前没有独立用户钱包、私钥管理、余额账本、出款签名、提币和用户钱包向平台转账能力。

本次建议覆盖：

1. 钱包创建、用户归属、平台密钥托管与备份恢复。
2. 按地址识别入账和出账、余额展示与对账。
3. 用户提币、开卡付款及其费用管理。
4. 付款确认后调用已有开卡流程，并提供人工异常处理。
5. 移除旧 Epusdt 订单支付流程。

暂不覆盖：其他链的实际接入、跨链桥、自动兑换、自动退款、卡消费账务，以及生产主网直接上线。首期设计和实现包含 Nile/主网配置隔离及主网适配边界，但实际部署和资金测试先在 Nile 完成，主网另行验收上线。

“卡消费账务暂不覆盖”仅适用于本轮 Nile 原型，不构成真实付费卡运营方案。生产前另行补齐供应商授权/清算/退款/费用数据、备付与履约责任对账；消费明细页面可分期，但资金与供应商对账不能随页面一起省略。生产产品的发卡身份、用户使用范围和项目权限须由供应商确认，不能用沙盒成功替代。

开卡款项全部保留在平台收款钱包，不设计逐笔 USDT→Airwallex 资金流转。平台在收款确认后，用入金部分对应的金额设置卡额度。

**设置卡额度不等于给 Airwallex 充值。** 当前开卡请求使用 USD、`transaction_limits` 和 `ALL_TIME` 限额，属于消费控制；实际消费仍依赖平台在 Airwallex 的可用资金或其批准的授信安排。供应商统一备付可以独立于每笔开卡收款进行，但主网上线前必须确认，不能仅凭额度设置成功就视为资金已就绪。沙盒不证明真实资金覆盖。

## 3. 总体架构

采用现有 Go 后端加模块化链适配器。首期共用 PostgreSQL，不引入多链平台或完整微服务体系；签名组件作为独立进程/服务部署，以隔离密钥访问。

```text
用户端 / 管理端
        │
Fcard 业务层：充值展示、提币、开卡付款、人工处理
        │
钱包管理 ── 账本与对账 ── 持久化任务与交易编排
        │                       │
        └──────── 链适配接口 ─────┘
                      │
               TRON 适配器（GoTRON）
                      ├── RPC / 广播 / 确认 / 费用估算
                      └── 内部签名服务 → 加密密钥存储

链监听器 → 统一链事件 → 账本、交易状态、业务流程
```

GoTRON 用于 TRON 能力，不负责其他链、Fcard 用户权限或业务账本。现有 HTTP RPC 和严格证据验证可提取并改造复用，不代表原代码已经支持主网或新钱包模型；具体限制见第 10.1 节，不要求为引入 SDK 全部改写为 gRPC。

实现前固定 GoTRON 版本，验证 Go 1.26、目标节点协议、助记词派生、交易构造和签名兼容性；核查所选版本的 LGPL-3.0 许可及分发义务。独立助记词派生方案已确定，具体库版本、参数和密钥保护部署仍需落实。

### 3.1 模块建议

| 模块 | 职责 |
| --- | --- |
| `internal/wallet` | 用户钱包归属、创建任务、地址和钱包可用状态 |
| `internal/asset` | 网络、原生币、代币合约、精度和启停配置 |
| `internal/ledger` | 分资产账本、冻结、费用、对账及调整记录 |
| `internal/transfer` | 提币和开卡付款的交易状态、幂等与恢复 |
| `internal/chain` | 共用类型、链能力接口和统一事件 |
| `internal/chain/tron` | GoTRON、TRON RPC、扫描、费用和确认规则 |
| `internal/signing` / 独立签名进程 | 密钥创建与加密、受控签名、平台备份恢复 |
| `internal/card` | 复用开卡，增加已付款前置条件和异常关联 |

不要求所有链实现完全相同的大接口。按地址校验、余额读取、交易准备、广播、确认等能力拆分；Energy、Nonce、区块有效期等细节留在适配器内。

### 3.2 进程、权限与资源边界

- 保持同仓库和模块化业务单体，HTTP、扫描 worker、资金执行 worker、签名服务可分别运行、暂停和恢复；首期不以引入消息中间件或全面微服务化作为依赖。数据库内持久化任务/事务 outbox 满足可靠交接后，再按实测容量决定拆分。
- HTTP、历史扫描、出款和对账配置独立连接预算、并发与超时，总连接数受数据库预算约束；补扫不能耗尽 HTTP 或资金事务的连接。链 RPC 使用全局配额与按任务保留的预算，不能让历史预取挤占未决交易核查。
- 签名服务独立运行身份和凭据，业务服务不能读取密钥材料或主加密密钥。签名服务只写自身受控的授权消费、签名尝试和审计记录，不依赖业务进程传入的“已授权”布尔值。
- 扫描、账本、授权和广播职责分离：链适配器提供证据与构造能力，账本决定记账；签名服务执行受限授权，资金 worker 负责受控广播。共享 PostgreSQL 不代表各进程可以任意写所有表，按角色限制写权限。
- 在第 11 节验收各进程异常退出、连接池耗尽和限流情况下的隔离效果；HTTP 存活不等于资金服务就绪。

首期实施形态采用独立入口：改造 `cmd/server` 运行 HTTP；新增 `cmd/wallet-worker`，通过受限的 `--roles` 选择 `scanner`、`ledger`、`reconcile`、`transfer` 任务；新增 `cmd/wallet-signer` 独立运行签名服务。上述新增命令为待实施约定。部署时扫描/记账与资金执行使用不同 worker 进程、数据库角色和资源预算，不以“同一个二进制”混用权限；开发模式可合并非签名 worker，不能绕过准入或获得签名密钥。

启动配置限制进程可承担的角色、网络及权限；运行期暂停采用持久化控制记录，区分全局/网络/钱包范围与人工暂停/故障阻断/恢复观察条件，包含原因、来源、版本、操作人和审计。准入取所有约束的交集，任一有效阻断都不得出款；自动恢复仅清除自身可恢复的故障，不清除人工暂停。管理 API 只能执行有权限、带版本检查的状态转换，不提供“无视证据冲突强制启用”。控制状态不可读取时资金执行拒绝准入。

暂停请求在受理、任务领取、最终签名和广播前检查，并由签名服务独立复核其负责的限制。定义控制版本、在途执行边界和暂停生效回执；不能承诺暂停按钮可撤销已签名/已广播交易。实例重启读取原暂停状态，不以进程启动默认解除。P1/P2 实现并验证角色隔离及暂停机制，P3 验证其覆盖所有资金执行入口。

### 3.3 派生库、交易 SDK 与备用方案

GoTRON 保持首选交易 SDK，密钥派生通过独立接口实现和验收，不让 P1 的钱包恢复能力绑定交易 SDK。P0 分别选择 BIP39、BIP32/BIP44、secp256k1、哈希与 TRON 地址编码的可靠实现，锁定版本、参数和测试向量；不能假定 `go-bip39 + go-ethereum` 自然组成完整的 HD 派生实现。验证已知向量、路径、前导零、地址校验及跨实现恢复一致性，不自行设计密码算法。

P0 核对所选 SDK 具体版本的 Go/节点兼容性、交易编码/签名正确性、许可与分发条件、必要接口及可定位的维护证据，不凭未注明版本的“维护活跃/不活跃”结论决策。派生和密钥持久化可独立做原型；真实交易签名前必须完成其所用交易栈验证。

若首选 SDK 的必要功能、兼容性、正确性或许可条件不满足且无法合理解决，形成带证据的替代决策，再评估“现有 HTTP RPC + 经过验证的协议编码/哈希/签名库”。HTTP 只提供传输/查询/广播能力，不代替交易构造与最终字节校验；备用方案必须通过同样的向量、回执、签名恢复及 Nile 验收，不能临时手写密码学代码或静默切换。替换不改变钱包派生参数、地址或既有尝试身份。

## 4. 钱包与密钥

### 4.1 环境与网络隔离

- 用户与钱包一对多；首期每个用户在所属环境拥有一个 TRON 钱包。测试环境仅启用 Nile，正式环境仅启用 TRON 主网，不在同一运行实例切换两者。
- 使用独立 ENV 文件选择环境，例如 `.env.wallet.test` 与 `.env.wallet.production`（文件名为建议）。启动时显式选择一个文件，不同时加载并混合覆盖；缺失或配置冲突时拒绝启动，不默认回退主网。
- ENV 分别配置环境标识、网络标识、RPC/凭据、资产合约与精度、平台收款/资源钱包、数据库、签名服务与密钥存储引用、扫描起点、金额限制等。实际 ENV 不提交仓库，另提供不含秘密的 example 模板；实施时同步补充忽略规则。
- ENV 用于环境配置，不存放用户助记词和派生私钥；这类用户密钥由签名服务加密管理。正式主加密密钥与密文分离保存。
- 测试/正式使用独立数据库、密钥存储及加密密钥、助记词、平台钱包和扫描进度；不得复制测试助记词或测试余额作为正式钱包初始化数据。
- 启动时核验实际节点网络/创世块与选定环境一致，核验合约及资产参数；签名服务同样绑定环境、网络和钱包归属，避免只改 RPC 地址就跨环境出款。
- TRON 主网和 Nile 地址格式相同，不能依靠地址前缀区分环境；页面显示环境/网络，后端使用受控网络配置决定查询、签名与广播目标。

### 4.2 每用户独立助记词与派生

- 每用户、每环境使用密码学安全随机数独立生成 BIP39 助记词，再通过 BIP32/BIP44 派生 TRON 私钥；禁止从同一平台主助记词为所有用户派生钱包。
- 建议首期使用 24 个英文助记词，TRON 派生路径为 `m/44'/195'/0'/0/0`；词数、路径、库及参数在技术验证后固定并版本化。不同用户可使用相同路径，因为其助记词独立；不靠路径索引隔离不同用户。
- 首期建议不使用额外 BIP39 passphrase；若采用，必须同样纳入加密备份和恢复元数据，不能依赖运行时人工记忆。参数建议不改变“每用户独立助记词”的已确定原则。
- 助记词及派生私钥仅由平台托管，不向用户展示或导出。派生私钥由签名服务使用，避免普通业务模块保存明文副本；如需持久化缓存，也必须加密并关联派生版本。
- 丢失派生私钥时，应能用该用户助记词及派生参数恢复原地址；助记词与派生私钥都丢失且没有可用备份时，不能仅凭用户账号恢复链上资金。
- 单个用户助记词泄露影响该助记词下的所有派生钱包，不扩散到其他独立助记词。未来多链若复用该助记词，也会扩大该用户内部的受影响范围；独立助记词并不能消除签名服务或解密权限整体泄露的风险。

### 4.3 托管、备份与授权

- 创建账号后使用幂等任务创建钱包；钱包未就绪时，账号可存在，但充值和转账入口不可用。
- 助记词及需持久化的派生私钥加密保存；普通业务接口和业务数据库记录仅持有密钥引用及非秘密的派生元数据。主加密密钥与密文分开管理，支持备份恢复与加密密钥版本轮换；加密密钥轮换不改变钱包助记词或链上地址。
- 用户端和普通管理端不提供密钥展示、交付、下载或导出接口；密钥不进入日志、URL、分析系统或浏览器。二次验证用于授权资金操作，不用于导出密钥。
- 平台密钥备份是运维职责，不设置用户备份助记词或确认备份步骤。钱包创建和平台可恢复性检查通过后即可展示充值地址。
- 助记词密文、主加密密钥和用户/环境/地址/密钥引用关系均有受控备份，备份包含派生路径、算法版本与所需参数；恢复演练验证助记词可以恢复原地址、签名能力及未决交易记录，避免丢失映射后重复建钱包或出款。
- 签名服务不接受任意交易字节直接签名；需独立检查网络、资产、来源钱包、目标、金额、费用上限、操作类型和授权记录，并防止重放。
- 用户提币与开卡付款须有明确业务授权；平台补充资源、人工退款等操作使用各自受限权限，不允许普通管理员通过任意签名接口绕过授权。
- 密码重置不会改变钱包密钥或地址，也不自动授权出款；重置、账号停用和权限变化后，未执行任务在签名前复核授权，已广播交易继续跟踪。链上地址不能仅通过修改数据库完成换钥。

独立进程只能减少密钥暴露范围，不能消除平台本身可转账的事实。正常情况下用户不能自行更改 B 的链上权限或外部支出；如发现未授权出账或权限变更，应暂停受影响钱包的新出款、保留链上事实并进入安全异常处理。平台冻结是内部执行约束，不是链上多签或合约锁定。

用户端仅提供钱包地址/二维码、网络说明、余额、流水、提币和开卡付款确认；管理端提供状态、任务、对账差异及人工案例，不展示明文私钥或助记词。

### 4.4 签名授权协议与防重放（P0 定规格，P1/P3 实施）

- P0 固定威胁模型及可信组件：分别说明普通管理员越权、业务数据库被篡改、业务服务失陷、签名服务或主加密密钥失陷时的防护范围。每用户独立助记词不能抵御共同解密权限失陷；独立进程、双人审批或一次性令牌也不能单独宣称解决所有场景。
- 资金授权具有稳定的 `authorization_id`、操作 ID、用户/钱包、环境/网络、资产与合约、精确目标及金额、费用资产/承担方/上限、用途、有效期、授权版本与二次验证凭据引用。修改关键内容须重新授权；二次验证方式、有效期、收款人变更保护和大额审批阈值由第 12 节定稿。
- 授权签发组件及其密钥/凭据与普通业务写权限隔离；签名服务独立核验授权真实性、二次验证的绑定和有效期，并维护不可被普通业务进程重置的消费记录。P0 选择可实现的信任路径，验证业务进程单独伪造/修改授权或重放旧授权不能取得新的任意出款签名；若首期不能抵御业务服务失陷，必须明确剩余风险和上线前补强措施，不能以同库状态读取冒充独立校验。
- 一份授权只允许一个逻辑资金操作。合法的过期重构使用受限的尝试版本，关联旧交易最终失效证据；同一尝试幂等返回原交易与签名，不允许换操作 ID 绕过一次性消费。
- 签名服务自行解码最终交易，校验来源地址/权限、网络引用区块、TAPOS 与有效期、合约与方法、收款地址、金额、附带 TRX、费用参数和操作用途。首期只开放明确允许的 TRX/指定代币转账及受控资源操作；禁止任意合约调用、代币无限授权和账户权限修改进入普通资金签名接口。不能只比对业务层的展示字段。
- 用户提币、B→C 付款、资源补充、C 钱包退款和平台运维分别设授权策略、单笔/累计预算、调用身份和暂停开关。高风险人工退款与平台钱包操作的申请、审批、执行分权，至少禁止申请人自行批准自己的高风险操作；具体双人审批门槛待确认。
- 签名服务调用采用经过身份认证的受限通道，设置请求大小、速率和审计约束；审计包含授权/尝试 ID、规范化交易摘要和策略版本，不记录秘密。全局、网络及钱包紧急暂停在最终签名前复核，不能仅在用户提交请求时检查。

### 4.5 备份、密钥轮换与灾难恢复

- 钱包密钥创建先使用稳定请求 ID 完成签名侧持久化，再绑定业务钱包。密钥材料、环境/地址/密钥引用映射与派生元数据达到规定备份条件、可找回原地址且扫描生效边界建立后，才进入地址可展示状态；失败重试不能生成替代地址冒充原钱包。
- P0 确定 RPO（可接受的数据丢失范围）、RTO（恢复时限）、备份频率、保留周期和责任人。对已经展示的地址，不接受不可恢复的密钥材料或归属映射丢失；业务账本允许的恢复点与重建步骤另外明确。不能仅声明“每日备份”而忽略两次备份之间新增的钱包。
- 密钥采用经审查的认证加密与密钥分层管理，具体实现和部署在 P1 验证；密文绑定钱包/环境/密钥版本等上下文，防止调换密文造成错误归属。记录主加密密钥和数据密钥版本、轮换过程及恢复所需元数据；备份权限与生产解密权限分开，不能将密文和解密凭据一起公开备份。
- 覆盖密钥、归属映射、账本、冻结、业务授权、签名尝试、已签名交易、未决广播、供应商请求和人工案例的恢复演练。既验证恢复原地址，也验证找回签名能力和未决操作，不能只验证助记词派生结果。
- 从旧备份或全新实例恢复后，默认关闭新出款和新开卡执行；核对签名侧记录、备份后链上交易及供应商操作，补扫/对账并排除重复执行，审核通过才恢复准入。恢复代码或数据库快照不能撤销链上付款。
- 区分加密密钥轮换与链上密钥疑似泄露：前者不改变地址；后者需独立应急方案处理钱包权限/资金迁移、旧地址后续入账和用户提示，不能仅换数据库密钥引用。平台钱包 C、资源钱包和退款钱包均纳入托管与恢复范围。

### 4.6 二次验证的阶段与最小交付

当前 `internal/userauth` 主要为密码/会话能力，不能估算成已有完整资金二次验证。P0 确定方法和恢复策略，首期建议账户绑定 TOTP 等独立第二因素，最终选型在第 12 节记录；再次输入同一密码仅属于再次认证，不能标记为双因素认证。采用 TOTP 时，验证码本身也不证明用户认可具体交易，须由第 4.4 节的授权服务把验证结果绑定到交易内容。

P1 定稿凭据/挑战/恢复数据模型和受限授权接口，P2 可并行实现绑定确认、验证、防暴力破解/重放、短时交易挑战、解绑及丢失凭据恢复。绑定秘密和恢复凭据不进入日志，账户恢复、管理员重置和换绑使旧资金挑战失效，并采用确定的通知/冷静期/审核规则；管理员不能仅修改数据库标记绕过用户验证。

P3 资金执行开放前完成用户操作界面、服务端交易绑定和签名侧验证联调，验收修改目标/金额、超时、重复消费、账号停用、因子丢失及恢复后的处理。纯技术原型可使用明确隔离的合成验证凭据，不得以测试绕过开关启用实际用户出款。二次验证与人工审批分别建模，审批不自动代替用户资金授权。

## 5. 数据与多链规则

以下为概念模型，最终 SQL 在方案确定后设计：

| 数据 | 关键内容 |
| --- | --- |
| `networks` | 链类型、主网/测试网、网络唯一标识、RPC、确认策略 |
| `assets` | 网络、原生币/代币、合约或资产标识、精度、启停 |
| `wallets` / `wallet_addresses` | 用户、环境/网络、独立助记词的密钥引用、派生路径与算法/参数版本、地址、状态、生效扫描边界；不保存明文密钥，不记录用户备份确认 |
| `chain_events` | 网络、交易、事件位置、转出/转入、资产、数量、确认依据 |
| `transfer_intents` / `transfer_attempts` | 业务目的、授权、幂等键、冻结、签名交易、广播及恢复状态 |
| `ledger_transactions` / `ledger_entries` | 追加记账、分录、资产、来源事件和冲正关联 |
| `balance_holds` | 平台待执行转账的金额及费用预留 |
| `card_payment_orders` | 入金、开卡费、其他费用明细、总收款、费用规则版本、USDT/USD 换算与舍入快照、目标卡 USD 额度、目标钱包、交易与开卡操作关联 |
| `reconciliation_cases` / `manual_cases` | 差异、未知结果、人工证据及处理记录 |

设计约束：

- 不能只用 `USDT` 标识资产；必须包含网络和合约。Nile USDT 与主网 USDT 严格隔离。
- 金额使用最小单位整数；共用存储须容纳大整数，例如受约束的 `NUMERIC(78,0)`，业务限额另外校验；API 以十进制字符串传递。
- 原生币和代币都建模：即使首期业务只支持 USDT，也要记录 TRX 费用和相关资金变动。
- 链事件去重包含网络标识、交易哈希及链定义的事件位置；一笔交易可以包含多个转账，不能只按交易哈希去重。
- 账本按资产平衡，冻结单独记录；禁止把不同网络资产或 USDT 与 USD 直接混记。
- 平台资金流与用户钱包资金流要分清会计主体。B→C 两端都被监听时，只完成一次付款，不重复增加用户余额。
- B→C 收款拆分为服务费用和对应卡额度的入金义务；入金部分不能因进入平台地址就直接全部确认为平台费用收入。具体会计科目另定；USDT 收款和 USD 额度以业务记录关联，不能在分资产账本中直接相加。
- 已记账流水不直接改写，错误通过有依据的冲正或补充分录修正。
- 新钱包绑定与扫描游标需要协调，回扫覆盖创建/绑定期间，不能因扫描已推进而漏掉首次充值。

### 5.1 资金责任与记账矩阵（P0 起草，相关模块实现前定稿）

B 地址、C 地址都由平台控制；B→C 不会自然减少平台控制的总 USDT。应按业务责任将用户钱包余额转为待履约款、服务费用或后续卡服务义务，不能把一次内部链上移动全部视为收入。以下定义记账效果，P0 起草具体借贷科目、会计主体和收入确认时点，按第 11.3 节在相关模块实现前形成逐项平衡分录；已确认的退款原则按第 8.4 节执行，未确认的费率与细则不在本版定价。

| 事件/阶段 | 资金与账本要求 | 必须保留的关联 |
| --- | --- | --- |
| 外部充值 A→B 连续核验成功 | 记录托管链上资产及对应用户余额责任；观察中金额不进入可用余额 | 网络/资产、链事件位置、地址归属版本、记账来源 |
| 提币或开卡付款预留 | 增加冻结，减少可用，不把冻结本身记成链上支出或已实现收入 | 操作 ID、金额/费用预留、报价/授权版本 |
| B 对外提币成功 | 按已确认本金结算用户余额及冻结，实际链费单独按承担方入账 | 唯一交易尝试、确认依据、费用分录 |
| B→C 付款成功，尚未履约 | 结算 B 钱包冻结和余额，C 收款对应待履约义务及费用明细；同一转账的两端只形成一次付款归属 | 付款订单、D/F/O 快照、原链事件、目标 USD 履约金额 |
| 供应商创建受理或卡不可用 | 不把待履约款自动清为收入，不仅凭 HTTP 成功消除退款/履约责任 | 供应商请求 ID、创建/卡/额度验证状态 |
| 卡可用且满足约定履约条件 | 按确定规则转结待履约款与服务费，保留对应后续卡服务责任；供应商备付独立对账 | 付款一次性消费、实际控制配置、履约时间与依据 |
| 交易明确执行失败 | 不扣除未转出的本金；已确认链费仍须结算，释放剩余预留 | 最终失败证据、实际费用、释放原因 |
| 签名/广播/供应商结果未知 | 保留相关冻结或待履约义务，不重复扣款、退款或记收入 | 原授权、原交易/请求、恢复任务 |
| 平台垫付资源、充值 TRX 与手续费 | 分开记录平台垫付/成本、用户资产和约定费用结算；链上可替代的 TRX 不靠标签解决可提规则，不默认补贴或可提现 | 来源资金钱包、预算、用户费用授权、实际消耗 |
| 人工退款 | 预留退款来源资产，形成独立退款义务与链上执行；不修改原付款事实 | 原订单、可退上限/累计已退与在途金额、审批与新交易 |
| 异常出账、账务更正 | 保存链上事实并记录差异，不伪造用户授权；用有依据的补充分录或冲正处理 | 差异案例、证据、审批及原分录 |

USDT 与 USD 分资产记账并通过业务订单关联；若入金 D 按报价兑换为 USD 履约金额，保存汇率方向、精度、舍入、有效期和差额承担方，明确转换后义务币种及退款采用原币原金额还是其他口径。平台承诺的卡额度不是链上资产，也不能直接加进用户钱包余额。

### 5.2 事务边界、唯一性与不变量

- 创建操作、检查余额、金额/费用冻结、幂等记录和任务/outbox 在同一数据库事务提交；按确定锁顺序处理用户、钱包、资产及冻结，跨钱包平台资源预算也须防超额。网络调用不持有长数据库事务。
- 连续核验块的证据、链事件和推进游标原子保存；业务记账可同事务完成，或由可靠任务消费。采用后者时分别保存证据游标、已归属/已记账进度及对账基准，资金准入以相关完整处理进度为准，不能仅因 RPC 数据已获取就宣称余额同步。
- 消费链事件时，账本分录、消费标记、业务状态及后续 outbox 原子提交；写平衡分录、更新余额投影和释放/结算冻结也必须有明确事务边界。投影可重建且有版本/检查点，不以异步未完成的投影承诺可用余额。
- 数据库约束覆盖：网络+事件位置去重；记账来源唯一；同操作同用途冻结唯一；用户/操作类型/幂等键唯一并核对输入摘要；一个付款只能被一个开卡履约消费；退款累计已完成和在途预留不超过可退额。同用户一个有效开卡名额通过锁与唯一约束保证，不只依靠先查后写。
- 每资产借贷平衡；正常冻结不能超过可用金额；最终结算/释放只能一次。发现未授权链上扣款导致资产不足时显式记差异并停出款，不能用修改历史或掩盖负数强行满足界面余额。
- 任务采用至少一次交付与幂等消费，不能依赖“队列恰好执行一次”。COMMIT 响应丢失后通过稳定操作 ID 查询实际状态；重复事件、并发请求、旧 worker 复活和重启重放都不得重复记账或再次创建外部操作。

P0/P2 配套一个可运行的账本验证原型（spike），在可销毁的临时 PostgreSQL 库中验证分录平衡、并发冻结、唯一约束、事件重复消费、冲正以及提交结果未知后的查询/重放。使用明确合成资金，不访问真实签名或广播；原型用于检验规格可执行性，其临时表与结论不能自动当作最终生产迁移已验收。

## 6. 入账、余额和对账

新方案以“地址属于谁”识别资金，不再依赖“订单要求转多少”。已支持网络和资产的实际到账金额按链上确认入账，例如充值 0.5 USDT 就记录 0.5 USDT。

需区分用户账本余额、平台待执行冻结、用户可用余额和链上已确认余额。用户可用余额以账本余额扣除冻结及适用的费用预留计算，平台实际可执行金额还受来源钱包链上余额、未决交易、资源与对账状态约束；不得仅查询 RPC 余额就允许出款。费用若由其他平台钱包承担，应在对应账户预留，不重复扣用户余额。扫描落后或存在差异时限制出款。

用户不持有密钥，正常出款全部经过平台，因此并发提币、开卡付款和费用扣款必须使用同一套事务冻结与来源钱包执行控制，不能各自独立扣款。链上监听仍是实际结果依据：发现无平台授权关联的出账时，先保留事实、记录对账差异并暂停受影响钱包的新出款，转人工调查；不直接将其认定为用户已授权提币，也不篡改账本来抹平差异。

监听至少覆盖：

- 外部充值到 B、B 对外转出、B→C、平台补充 TRX 以及实际手续费。
- 平台授权发起的交易，以及无法关联平台操作的异常出账；不再设计用户持有 B 密钥的外部支出流程。
- 支持资产以外的转入：不自动当作 USDT 入账，提供可观察记录和人工处理线索；首期展示范围待定。

复用现有持久化游标、补扫、完整回执校验与去重，增加地址归属和出账处理。定期用链上余额核对账本，明确对账高度/时间，区分扫描延迟与真实差异。

其他链使用各自的确认和重组处理策略，不复制 TRON Solidity 规则。

### 6.1 扫描性能与追平（P2 待实施）

保留连续核验、完整回执校验、持久化断点和事件去重，将现有扫描能力提取到 `internal/chain/tron`。以下是后续开发与验收要求，不表示当前扫描器已具备全部能力。

- 先测量 RPC 各接口耗时和错误率、每块交易数、每秒完成核验的区块数、数据库提交耗时、请求量和证据存储增长，区分节点、核验与数据库瓶颈；记录代码版本、节点套餐/限流、网络和机器配置，形成可复现基线。
- 区块与整块回执采用有上限的并发预取，按高度连续核验和提交；按节点已验证的能力优先使用整块回执接口，核对交易与回执一一覆盖，不能漏回执或接受重复、额外回执。并发、超时、批量和全局请求速率均可配置。
- 同一批次复用已校验的链头、区块与回执，减少重复请求；复用须校验网络、区块身份和父子关系，不能跨网络或把过期链头当作最新同步状态。多个扫描任务共享节点请求预算，避免相互放大限流。
- 区分历史追平与实时监听：历史追平在节点预算内提高并发；追平后降低空轮询频率。遇限流或超时按退避和抖动降速，队列、内存和落盘缓存均设上限并实施背压，不能为了持续预取耗尽资源。
- 若评估按地址或事件索引加速，必须证明覆盖全部受管地址、相关入账/出账和费用，且可发现缺页、延迟与重复，并保留区块连续性和回执复核。不得直接用第三方地址列表替代完整到账依据，也不能仅过滤交易的顶层目标地址而漏掉合约内部转账。

P0/P2 在选定节点上锁定以下容量目标；建议起点为历史扫描持续处理不少于 10 块/秒、连续压测至少 30 分钟，约 24 小时的历史积压在 60 分钟内追平（包含追赶期间新增块）。实时模式相对最新可信固化链头的同步延迟建议 P95 不超过 30 秒、持续观测至少 30 分钟。记录区块交易密度、实际限流和资源峰值；节点条件无法支持时先调整容量或明确修订目标，不能把本机短时测速当作上线承诺。压测须同时验证登录/查询响应、核验完整性及去重，不以跳块、重置断点或放宽证据规则换取吞吐。

### 6.2 单块异常、故障隔离与恢复（P2 待实施）

扫描故障不应退出整个 HTTP 服务。分别管理网络扫描器和资金 worker 的生命周期，隔离登录、查询、管理端和其他网络；扫描器异常退出由监督任务记录状态并按故障分类处理，不能无限快速重启。

| 故障 | 处理与恢复 |
| --- | --- |
| RPC 超时、连接中断、限流或短期回执缺失 | 持久化重试状态，有限次快速重试后进入退避探测；遵守节点重试提示并设置请求超时。持续故障告警，worker 保持可恢复；恢复取证后从原断点继续，无需重启整个后端 |
| 未支持的交易类型、无法解释的回执或证据冲突 | 保存故障高度、区块/交易标识、原始证据及策略版本，进入待审核；不得自动判为无资金影响或跳块。审核最小核验策略、补充真实样本与异常回归后，受控重放原高度 |
| 节点网络身份错误或链连续性冲突 | 暂停受影响网络的资金操作并告警，核对网络身份、可信链头和原检查点；不能通过自动换网络、改起点或忽略冲突恢复 |
| 数据库不可用或提交结果未知 | 限制预取并退避；恢复后读取持久化进度，幂等重放待提交批次，确认实际提交结果，不重复记账 |
| 进程或 worker 异常退出 | 通过持久化检查点、异常案例和任务状态恢复；使用单写者控制及执行版本防止旧实例覆盖新进度，重启不漏扫、不重复入账 |

分别记录“已获取数据的高度”和“已连续核验并提交的高度”。单块未解决时可在资源上限内继续预取后续数据，但不得越过缺口推进正式游标、账本入账或对账基准，也不得宣称已追平。界面可展示后续观察线索为未核验信息，不能计入可用余额。

故障案例至少记录网络、scanner、区块高度/哈希、交易哈希（如有）、错误分类、首次/最近发生时间、重试次数、下次重试时间、证据引用与核验策略版本。人工恢复须有操作权限、原因、证据和审计；仅允许重新核验或经审核的策略更新，不提供“忽略此块并推进”或“强制到账”入口。故障证据受访问控制，日志不含密钥、RPC 凭据或其他秘密。

### 6.3 暂停范围、同步状态与告警（P2/P3 待实施）

钱包扫描落后不会阻止链上真实转入。界面必须提示到账确认延迟，显示最后核验高度、时间及暂停原因，不得将旧余额显示为实时余额，也不得把服务不可用显示成零余额。新钱包的扫描生效边界和备份恢复条件未满足时，不展示充值地址。

暂停范围按已证明的影响决定：可证明仅影响单个钱包时暂停该钱包的新资金操作；未知交易类型、区块缺口或全网扫描不可信且无法证明影响范围时，暂停该网络的新提币、B→C 开卡付款及其他新出款，保留登录、查询和无依赖的其他网络服务。首期采用网络级暂停作为保守起点，不能仅凭异常交易顶层地址与受管地址不同就缩小范围。新开卡调用必须等待对应付款连续核验成功；已广播交易继续只读跟踪与核对，未知结果不释放冻结、不重签替代交易，不自动执行积压的新出款。

运行状态至少区分启动中、追平中、就绪、退避重试和待人工审核；健康接口分别暴露 HTTP 存活、数据库状态和各网络扫描/资金准入状态，避免扫描暂停被表现成整个站点失联。钱包接口返回明确原因码、最后同步高度和时间；前端在未就绪期间定期刷新，并明确区分配置关闭、正常追平和故障暂停。

建议初始阈值：可信固化链头与最后完整记账块的时间差超过 60 秒预警，超过 120 秒暂停该网络新出款；连续 30 秒无法获得可信链头也暂停。同步监测链头本身的新鲜度、最近高度推进时间和本机时钟偏差；节点一直成功返回旧链头不能视为正常。链头陈旧或多来源不一致时按第 6.6 节处理，具体阈值经节点能力验证后定稿。扫描证据冲突或进入人工审核时立即暂停，不等待滞后阈值。

暂时故障自动恢复须满足：故障已消除、链身份与连续性复核通过、持久化状态一致、同步延迟连续至少 60 秒处于就绪阈值内，且无未解决的资金差异或人工暂停标记。人工审核类故障还需有权限的审核结论，不能仅因节点恢复便自动解除。恢复准入后，具体出款仍重新检查授权有效性、余额、冻结、租约和费用条件。

告警至少覆盖证据冲突、连续失败、滞后超阈值、队列/存储接近上限及 worker 意外退出；按网络和故障去重，持续未解决则升级，恢复时发送恢复通知。上线前指定告警接收渠道、值守责任人、确认/升级时限和恢复操作手册；监控应独立发现整个扫描进程失联。保留故障期间 API 可用性与处理记录，供事后核查。

### 6.4 性能和故障验收（P2 必须完成）

- 在固定节点预算下完成历史追平与实时监听压测，输出吞吐、P95 同步延迟、RPC 请求量、数据库/缓存/存储资源和 API 响应数据，验证第 6.1 节最终确定的目标。
- 注入超时、限流、单块回执缺失、未知交易、冲突链头、数据库中断和提交响应丢失；验证正常退避、告警与恢复，且每种情况下正式游标不跨缺口、不提前到账、不重复记账。
- 未知交易卡住单块期间，登录/查询继续可用；后续预取保持有界，受影响网络新出款被阻止，其他网络无依赖操作继续；待审核状态不会无限自动重启。
- 注入进程重启、重复重放和旧 worker 复活，验证断点、单写者控制和幂等；新增钱包与扫描并发时不漏首次充值。
- 覆盖配置关闭、追平、暂时故障、人工暂停及恢复稳定窗口的界面/接口行为；恢复后无需用户反复重启服务或手工刷新页面才能看到状态变化。

### 6.5 完整交易分类与协议兼容（P0 验证，P2 实施）

不能把“凡不在入金类型白名单内就停整个扫描器”作为常规运行策略。依据锁定的 TRON 节点/协议版本建立全部已知交易类型的版本化分类清单；未知或证据冲突保留为最后防线，不通过忽略交易规避。分类清单至少包含原始类型、可能执行合约与否、原生币/资源/账户权限影响、所需回执和事件、成功/失败规则、资金归属及异常处理。

| 类别 | 核验与处理要求 |
| --- | --- |
| 智能合约调用和部署 | 校验执行结果、交易/区块/回执关联，提取所有受支持代币的相关事件，不依赖顶层目标地址；失败执行不产生成功入金，但保留实际费用 |
| 原生币或原生资产转移 | 记录受管钱包实际收支及手续费；TRX、其他资产与 USDT 分开，不能把非 USDT 操作统一解释为无资金影响 |
| 质押、解质押和资源委托等 | 记录与受管钱包有关的余额/资源变化，不生成 USDT 入金；普通用户钱包不开放的操作若真实出现，应保存事实并按未授权行为处理 |
| 账户权限变更 | 发现受管地址参与即进入安全案例，暂停相关钱包出款，复核签名权限；不能仅因不含代币日志而当作无影响 |
| 已验证的账户信息或治理操作 | 按具体协议语义核验；只有确认不会执行相关资产转移且无异常回执时，才按明确规则通过。此前的 `UpdateBrokerageContract`、`AccountUpdateContract` 须有样本覆盖 |
| 尚未识别的类型或回执变体 | 保存原始证据、分类/策略版本和故障位置，触发审核与适当范围暂停；不能通过猜测类型或仅比较顶层地址推进记账游标 |

P0 选择代表性历史区间回放，覆盖已知类型、成功/失败变体和高交易密度块，并记录未覆盖项及关闭条件。P2 验收不能仅依靠少量合成样本；节点/SDK 升级前执行兼容回放，新策略经审核和回归后重放受阻区块。分类变更保留版本，不静默重解释已入账事实。

已核对样本状态：`UpdateBrokerageContract` 在区块 `71809560` 有公开证据，现有规则及离线回归保存在 `tron_scan.go`、`tron_brokerage_test.go` 和 `testdata/nile-block-71809560.json`；提取到新模块后仍需验证。`AccountUpdateContract` 在区块 `71815003` 已取得公开样本，当前未纳入旧扫描白名单，分类实现和回归属于 P2 交付。它与修改账户权限的 `AccountPermissionUpdateContract` 是不同操作，后者已有旧白名单规则；不能互换名称或因此忽略权限变更风险。迁移样本只保留公开证据，不把本机 `.cache` 当作正式测试依赖。

复用现有 `tron_prefetch.go` 的并发预取和整块回执模式，先测量现有实现再优化；提取公共取证能力时去除旧订单金额/时间匹配。事件归属、用户余额和新钱包创建边界按新模型验证，不直接沿用旧订单归属。

### 6.6 节点可信性与同高度对账

- P0 实测所选节点的 Solidity 接口、历史区块/整块回执、限流和历史状态能力；特别验证能否读取指定固化高度的账户及代币余额。SDK 存在对应调用不代表节点套餐提供该能力，普通当前余额查询不能冒充历史高度快照。
- 明确主取证节点、独立核查来源和切换条件。创世块校验防止跨网络配置，但不单独证明回执完整、链头最新或节点诚实。关键分歧保留双方证据并暂停受影响操作，不能选择更有利的响应推进；同一供应商的两个 URL 不默认属于独立来源。
- 分别观测链头高度/时间、取证时间、连续核验进度、完整记账进度及可信度；针对节点持续返回旧链头、时钟偏差、临时链头停滞和真实网络停止规定告警与恢复规则。当前高度减扫描高度为零，不足以证明服务健康。
- 对账比较同一高度/时间口径的托管链上资产、用户钱包责任、冻结、待履约款及平台自有资金，并另对供应商备付/授信和 USD 履约责任。新充值在链上已确认但尚未入账、待广播冻结和链费在途状态分别解释，不允许仅比较两个实时总余额。
- 如节点不支持可靠历史余额，P0 选择有证据的对账方案，例如支持历史状态的数据源，或经过验证的一致性快照流程；明确锚定高度、读取期间发生的变动及补偿校验，不能把逐个钱包查询的混合时点结果标成同高度快照。方案未验证前不能声称已完成严格对账。
- 证据存储定义保留期限、原始数据/摘要/索引分层、完整性校验、归档和重放能力。清理不得破坏未决交易、人工案例或在保留期内记账来源的可追溯性；对账差异的容忍精度、责任人和结案权限在 P0 定稿。

## 7. 提币与交易可靠性

建议流程：

1. 用户选择网络和资产、填写地址及金额，查看预计费用和实际扣款。
2. 后端验证本人权限、钱包归属、链状态、余额和限额，完成二次验证；授权绑定网络、资产、目标地址、金额及可接受费用，修改这些内容后重新确认。
3. 在数据库事务中创建幂等转账意图、金额/费用预留和持久化任务。
4. 同一来源钱包串行准备交易；签名前复核账号状态、业务授权和预留，重新查询余额、资源和在途交易，按费用上限构造交易。
5. 签名后先持久化交易标识与可恢复的已签名交易，再广播；敏感交易载荷限制访问。
6. 后台跟踪链上结果，确认成功或明确失败后结算金额、费用和预留。

建议分开记录业务状态和链状态：

```text
业务：待验证 → 已预留 → 执行中 → 成功 / 失败 / 人工处理
链上：待构造 → 已签名 → 已广播 → 待确认 → 成功 / 执行失败
                                  └── 结果未知 → 查询恢复
```

关键规则：

- 广播超时不等于失败，不能立即释放资金并重新签一笔。
- 先查已保存的交易标识；需要重发时优先重播同一笔交易。
- 过期后重新构造，必须依据该链的有效期和确认规则证明旧交易不可能再执行；无法确定则人工处理。
- 幂等键重试返回原操作；相同键不同金额、地址或资产应拒绝。
- 失败交易也可能产生费用，必须按实际链上结果记账。
- 所有平台资金任务共享来源钱包的并发控制，包括提币、开卡付款和运维资金操作；内部冻结不代表链上执行必然成功，仍需处理资源不足、权限异常和节点故障。
- 链结果未知时只冻结相关资金和受影响操作，避免对同一资金重复出款。

### 7.1 签名、广播与取消的恢复协议

- 区分稳定业务操作 ID、授权 ID、交易尝试 ID、尝试版本与链交易哈希；准备交易时固定构造参数和有效期。签名侧按尝试幂等，在向调用方返回前持久化可找回的交易与签名结果；业务进程崩溃后能按尝试 ID 查询原结果，不能直接再构造一笔替代交易。
- 覆盖“签名侧已签名但响应丢失”“业务侧尚未保存签名便退出”“已保存待广播任务但未发送”“节点收到交易而广播响应丢失”四个窗口。业务侧先保存可恢复签名交易和待广播任务，再由有权限的资金 worker 广播；签名服务和普通 HTTP 进程默认不广播，凭据与网络访问策略按该边界设置。
- 准备、签名、广播和恢复都检查钱包执行令牌/尝试版本；租约过期不能授权新 worker 生成第二笔交易。TRON 首期同一来源钱包保守串行，上一笔存在可能执行的未决交易时不创建相冲突的替代尝试；资源钱包、C 与退款钱包同样受控。
- 只有能证明尚未产生有效签名，或旧交易最终不可能执行，才允许取消并释放相关预留；签名生成是否成功不明时先查询签名侧持久化记录。已经签名的交易可能仍被提交，仅有“系统尚未广播”的记录、内部取消标记、授权到期或账号停用都不会自动撤销链上执行能力；无法证明时保留冻结并查询，不把“当前查不到”当作失败。
- 报价有效期、用户授权有效期、链交易有效期分别保存。报价受理前过期则拒绝；受理后按已授权上限执行，超上限需重新确认。重置密码/停用账号使未签名操作停止并复核；已签名或已广播操作按实际状态核查，后续开卡/退款走各自授权规则。
- 一个逻辑操作可能有经证明合法的多个过期尝试，但最终资金执行只允许结算一次。旧交易失效证明、重新授权条件、重构权限及审计格式在 P0/P3 定稿并测试，不能把通用自动重试直接套在链上转账。

## 8. 开卡付款与人工处理

### 8.1 已确定的收费与额度规则

- 开卡入金 `D ≥ 50 USDT`，最低门槛针对入金部分，不是总收款，也不限制用户给 B 的普通充值金额。
- 总收款 `T = D + 开卡费 F + 其他费用 O`，三者均进入 C；链上手续费单独按第 9 节政策处理，避免重复收费。
- 卡额度仅由 D 换算得到，F 和 O 不增加卡额度；前端分别展示各项及总扣款。
- USDT 收款与 USD 卡额度的换算规则、舍入、报价有效期需确定。若采用 1 USDT 对应 1 USD，必须作为明确的平台报价规则保存，不能视为技术上天然等价。
- 示例（仅用于说明）：D=50、F=5、O=0，则向 C 收取 55 USDT；若已确定 1:1 报价，创建卡的 USD 限额为 50，不能设置为 55。开卡费 5 不是已确定的费率。
- 当前固定 `AIRWALLEX_CARD_LIMIT_CENTS` 应改为已付款订单的额度快照，保留独立的系统最大限额及沙盒限制，不允许前端直接提交任意卡额度。
- 开卡费用的实际数值和收取条件仍待配置；开卡失败退款按第 8.4 节实现。后续卡充值、消费后剩余额度及已消费卡的关闭/退款属于另行设计范围，不能把创建时的 ALL_TIME 限额当作实时余额。

### 8.2 执行流程

1. 报价前检查账号、钱包/网络、公司发卡身份、供应商可用性和用户开卡名额，检查 D≥50 USDT；快照保存网络、资产、D/F/O、费用/退款条款版本、汇率与舍入、目标 USD 额度、平台目标钱包和有效期。报价不等于已占用名额，受理时须在事务中重新检查并预留。
2. 用户明确确认明细后，在同一事务中预留开卡名额、总收款及适用手续费并创建付款任务；绑定报价、授权、钱包、付款订单与唯一开卡操作。报价未受理前过期不得付款；已受理、已签名/广播或待核查不得因原报价过期而自动释放名额。
3. 执行 B→C 转账；连续核验及付款记账完成后进入待履约状态，以唯一付款关联驱动开卡操作。请求使用订单的目标 USD 额度，此流程不向 Airwallex 转移本笔收款。旧创建接口和人工入口不得绕过付款一次性消费与资格检查。
4. 按第 8.3 节分别跟踪创建请求、卡状态和额度验证；超时先核查原请求，重放必须验证供应商幂等约定，不生成新 request ID 绕过未知结果。保留订单、供应商请求、卡及付款关联。
5. 卡可用且实际配置满足约定履约条件才完成付费订单；供应商明确失败、账号变化或配置异常进入人工案例。确认失败且排除可用卡后按第 8.4 节退款；UNKNOWN 不直接重新扣款、重新开卡或退款。

人工处理可以是核查后继续开卡、关闭案例或发起单独退款流程；不得直接将链上失败交易改为成功。首期不自动退款，人工退款如通过系统发起，也必须有独立授权、转账记录和账本分录。

正常 B→C 只能由已授权的平台操作发起，不提供用户通过 B 的密钥自行付款的流程。发现无法关联付款订单的 B→C 转账，或用户从外部 A 直接转账到 C，均不自动开卡，进入未关联收款人工处理。

### 8.3 供应商履约状态与备付对账

分别持久化付款、创建请求、卡、配置验证与退款状态。推荐正常路径为“付款确认并记账 → 待履约 → 创建请求受理 → 卡已创建 → 卡可用且配置已验证 → 履约完成”；任一步均可进入待核查，明确失败走人工处置。请求被受理、卡记录存在、HTTP 成功或 `provider_operation=SUCCEEDED` 均不单独代表履约完成。

- 现有 `internal/card/worker.go` 的 `matches()` 接受 PENDING/FAILED/INACTIVE 等合法状态，创建操作成功可表示得到供应商记录；复用时须与付费订单状态拆开。不能把现有 SUCCEEDED 直接用于释放待履约义务、确认收入或拒绝退款。
- P0 开始核对供应商状态定义、实际生效额度与币种的读取方式、程序/身份绑定、request ID 幂等范围和保留期限，以及按请求查找未知操作的能力；尽早识别架构风险，最迟 P4 集成开发准入前完成详细验证，不阻塞无依赖的密钥/派生原型。现有 `internal/airwallex/client.go` 响应模型不含完整控制配置，P4 必须补读取/验证能力或明确供应商可接受的替代证据；不可验证时保持待核查，不假设请求值已生效。
- 校验返回卡所属身份、请求与本地订单、实际 USD 控制金额及周期、其他必要限制。供应商的 PENDING、INACTIVE、FAILED、BLOCKED、CLOSED 等按正式语义映射，不统一认定为成功；“可用”条件及身份状态复核在 P0 调研、P4 集成准入前定稿，现有暂时跳过 READY 的沙盒做法不自动沿用正式流程。
- 供应商状态采用受认证的事件通知加定期拉取核对，按实际产品接口能力实现。通知验签/认证、防重放、去重、乱序处理、任务恢复和事件丢失后的补偿均有验收；若首期无可用通知接口，以有界轮询和人工核查实现，不虚构 API 能力。
- 开卡超时后“暂时查不到”不能证明未创建。UNKNOWN 保留付款与名额，查询原请求或人工核对；只有证明原请求不会再创建卡，才允许新尝试或退款。不能依赖固定次数重试来代替供应商幂等和最终状态证据。
- 明确平台 USDT 储备、供应商可用备付/授信、已承诺 USD 履约额度和实际卡责任的对账及资金覆盖口径，不能把 ALL_TIME 限额直接相加当成未消费余额。备付不足时停止新付费开卡受理，已付款款项保留义务并处理，不仅显示供应商报错。
- Nile 原型验证状态流转和异常处理；生产前须核实发卡身份与项目用途、正式产品权限、授权/清算/费用/退款数据、供应商资金覆盖及后续对账。完整消费页面可另期交付，真实资金运营的对账责任不能延期省略。

### 8.4 开卡失败退款（原则已确认，P0 起草细则、P4 准入前定稿）

已确认原则：开卡明确失败且排除仍可能提供可用卡的结果后，开卡入金 D 全退；已发生服务费只能按用户事先接受的约定扣除。首期由人工核查和授权退款，不启用自动退款。未知结果、创建受理中或仅暂不可用不直接当作最终失败，须按第 8.3 节确定是否还能履约。

- D 全退不因服务费扣除而减少。开卡费 F、其他费用 O 各自定义服务内容、发生节点、可扣条件、实际发生证据和最高可扣额，并随报价保存条款版本；未约定、未发生、无证据或重复计费的部分不可扣。已付 D/F/O 对应的总可退额为 D 加未合法扣除的 F/O，并扣减已经完成和仍在途的退款，不能把相同费用重复扣在不同退款中。
- B→C 转账实际链费和退款链费与服务费分开列示。退款链费由谁承担、以何币种结算及是否另行收费尚待确认；不得通过从 D 中暗扣链费破坏“入金全退”。失败前发生的费用与退款费用分别有报价/授权依据及上限，平台资源实际成本不自动等于可向用户扣款金额。
- 默认建议原 USDT 入金币种退款；退款到原 B 钱包、用户核验后的外部地址或其他渠道及具体流程在 P0 确认。退回 B 按真实链事件恢复用户余额，并与原退款义务结算关联，不能人工加一次余额、扫链后再加一次；外部退款按受控出款结算，不增加 B 余额。
- C 或指定退款钱包先预留足够本金及链费，再生成独立退款操作，沿用二次授权/审批、来源串行、签名与广播恢复及累计退款上限。目标地址变更须重新核验与授权，不直接相信管理员临时填写的地址。
- 退款和开卡完成通过订单锁/版本及互斥执行条件协调；审核退款前核对原供应商操作不会产生可用卡或已完成必要处置。出现迟到成功等冲突时冻结后续执行、保留双方事实并建案例，不能同时完成退款和履约；单独的人工结案按钮不能消除未清偿义务。
- P4 验收全额 D 退回、服务费部分扣除有证据、UNKNOWN 不退款、并发退款不超额、退款响应丢失不重复出款，以及退回 B 不重复记账。

### 8.5 人工处理的操作形态与阶段

首期交付受权限控制的管理端页面及配套 API，不以直接改表、仅打印审计日志或模型存在代替人工处理可用。P1 完成案例、证据、申请/审批/执行分权及审计模型；P2 提供扫描异常/差异查询和暂停状态页面；P3 提供未决交易核查与有权限的暂停/恢复操作；P4 完成付费订单详情、供应商 UNKNOWN 核查、退款申请/审批/执行及状态跟踪。页面可复用现有管理布局，旧 deposits 页的订单模型和权限不直接沿用。

每项操作显示业务/交易/供应商状态、证据、原因、金额、目标、剩余可退额、审批人和执行结果，并做服务器侧权限、版本、幂等和资金准入校验。恢复只能发起重新核验或清除有权限处理的暂停条件，不能强制到账；退款审批不绕过签名或累计金额限制。P4 验收由实际受限管理员完成完整操作、越权/重复审批被拒绝，并确认申请人与执行权限符合已定分权规则。页面未就绪前只允许隔离环境的技术验证，不能宣称人工退款闭环已交付。

## 9. 手续费与运营成本

已确定首期由平台先提供 TRX/资源，用户按报价承担链上费用并设置实际费用上限。具体费用扣款币种、换算、失败费用和退款费用规则在 P0 定稿；不采用用户必须先自行购买 TRX 的默认流程，也不默认平台承担全部链费。

- 钱包本地生成不产生链上费用；链上激活和实际转账另外计算，优先按需激活。
- TRON USDT 转账消耗 Energy 和 Bandwidth，按交易估算并设置上限，不使用固定“每笔必然多少 TRX”的假设。
- 若平台补充 TRX，需要单独的平台资源钱包、限额、幂等任务和记账；区分平台资源补贴与用户可提现资产，不能将补贴自动增加为用户可提余额，也不能重复补充。
- 首期不自动购买/租赁资源；后续根据交易量评估质押、委托和资源服务。
- RPC 容量需按用户钱包数、扫描方式、每日转账量评估；沿用全块回执扫描需关注请求量与存储增长。
- 初期采用托管节点，不自建全节点；费用预算按日活、每日提币/开卡笔数和已确定的垫付模式测算，具体计价和上限在 P0 定稿。

### 9.1 资源供给、费用报价与结算

- 分别测量钱包激活、B 提币、B→C、平台资源补充和 C 退款的费用/资源条件。用户地址已生成不代表可直接完成 USDT 转账；按需激活的时点、激活成本和失败处理须用所选节点与真实 Nile 场景验证，再验证主网差异。
- 报价列明用户费用扣款币种、金额或计价方式、最高授权扣款、有效期、费用承担方及失败时可能发生的费用；若用 USDT 收取 TRX 成本，保存 TRX/USDT 价格来源、时间、精度、舍入和失效规则。用户费用预留与平台资源/费用预算分别冻结，不把内部账本额度当作来源地址链上可执行资源。
- 签名前检查来源地址激活、可用 TRX/资源、未决交易和平台供给预算；费用估算设置合理余量但不突破授权上限。无法在上限内执行时保持未执行或请求用户重新确认，不静默扣更多费用，也不自动把平台欠款记到用户余额。
- 平台资源钱包设置来源串行控制、单钱包/用户/日/平台总预算、供给请求幂等和异常熔断；防止反复失败、重复补充或小额恶意操作耗尽平台 TRX。用户资金操作与资源供给分别记录状态，供给成功不代表目标付款成功。
- 按确认回执核对实际消耗及已约定的费用规则，结算费用预留、释放未用部分；不能仅按估算值宣称实际费用。费用是否固定报价、实际成本加约定费用或按成本结算须在 P0 明确；任何加价属于明示收费，不混入“实际链费”。失败交易已消耗的费用与未转出本金分开处理。
- 平台垫付 TRX/资源不是用户充值，不能直接增加用户可提余额；未消耗 TRX 的归属、用户自充 TRX 与补充资金混用时的扣费顺序/可提现规则，以及是否存在资源回收操作必须明确。若涉及回收转账，纳入独立授权及真实费用，不能靠数据库标签宣称链上资金不可转走。
- 按活跃钱包数和实际提币/开卡笔数估算平台 TRX 周转、链费、RPC 和证据存储成本，分别验证低余额、大量钱包与高峰场景。与供应商 USD 备付预算分开，禁止把 C 钱包 USDT 余额等同于所有执行资源已充足。

### 10.2 过渡期运行与入口切换

本项目不维持旧 Epusdt 与新钱包的常态双轨收款。旧流程确定弃用后，先完成旧测试订单、实际测试币及未决交易核对和必要证据导出；最迟在新钱包 P2 扫描启用前，关闭旧订单创建、旧 scanner 及其他 deposit worker，确认旧进程退出。旧任务的停止不推迟到 P5；P5 执行最终删代码/表/配置、持续运行和灾难恢复验收。

- 未结测试单由受控核查形成处置记录，不将其作为新钱包余额迁移，也不通过忽略真实测试资金去向直接宣称结清。若另需只读查看，保留历史查询/导出即可；“只读”不代表旧扫描 runtime 继续取证和写表。新旧表并存时写入权限及实例启动必须阻止已停旧任务复活。
- 新钱包使用独立扫描标识和经审核的生效起点，结合地址首次展示/绑定边界回扫；不静默继承旧订单归属。启用前检查新扫描角色、RPC/DB 预算、暂停控制、告警和环境身份，迁移与启动顺序不得让旧进程写已删除表。
- 旧流程停用后，首页充币入口和旧创建 API 立即停止受理；新钱包未满足第 11.3 节地址展示条件时显示未开放及原因，不回退公共旧收款地址。P2 钱包/扫描/记账验收通过后直接切到新地址/二维码及钱包状态；提币 P3、付费开卡 P4 分别开放，无资格的旧开卡接口同步禁用。
- 旧记录可按需查询期间明确标识为历史测试订单，不与新账单/余额混合。P5 移除已替代的旧页面、回调、健康检查与网关依赖，清理前再次核对证据保留清单；历史入口不得重新创建订单。
- 切换后仅新钱包健康状态参与资金准入。告警、监控和文档同步更新，避免旧 runtime 的 admission 状态仍驱动新 UI。新方案出现故障时暂停并前向修复，不自动重新启用旧收款作为回退。

### 11.2 持续运行与生产前独立准入

第 6.1 节的 10 块/秒、30 分钟压测等为候选基线，须覆盖高交易密度、限流、完整记账/对账负载、HTTP 并发、进程重启和节点长时间中断。P5 建议至少连续运行 72 小时并执行多次故障/恢复演练，记录吞吐、尾延迟、资源峰值、存储增长和人工案例处理；最终观察时长与容量按选定部署定稿，不能仅凭短时平均速度通过。

Nile 闭环完成不等于生产可上线。生产前单独确认正式供应商权限、资金覆盖与卡服务对账、主网资产/节点行为、主网费用及资源差异、授权/签名与备份恢复、值守及应急权限，并制定受控小额验证与逐步限额提升方案。该准入不授权本轮自动连接主网或发送真实资金。

| 节点与对账证据 | 实测历史余额能力，选择同高度对账方案、独立核查来源、链头陈旧阈值和证据保留期限 | 不能用当前余额或两个同源 URL 冒充可信历史对账 |
| 后续优先支持哪条链 | 暂不实施，确定后验证适配器边界 | 是否需提前兼顾 EVM/其他模型 |

托管模式、不向用户交付密钥、每用户独立助记词派生私钥、Nile/主网 ENV 隔离、开卡入金最低 50 USDT、D/F/O 均进入 C、仅 D 对应卡额度、开卡失败 D 全退且已发生服务费按约定扣除，以及平台先提供资源、用户按报价承担费用并设上限均已确定，不再作为待选项。P0 起草第 11.1 节五项规格，按第 11.3 节固化依赖部分；本表未决细则逐项记录为批准、待定或禁用，不以代码默认值代替业务决定。

## 14. 基于当前功能与 UI 的评估（2026-10-15）

结论：托管钱包、链上证据校验、冻结与幂等恢复的方向合理，但方案目前仍不足以直接实施。主要缺口在产品数据契约、付费开卡前置条件、账务细节和异常操作权限。以下均为待实施建议，不代表本次已新增资金功能。

### 14.2 P0：付费开卡前预留资格与名额

现有每用户最多一张未关闭或待核查卡，且服务受启用状态、公司身份配置约束。v0.6 已将收款前资格检查和名额预留纳入第 8.2 节：报价时预检、受理时重检，并在用户确认受理付款的同一事务中预留名额和资金，避免两个并发付款都成功、只有一个能开卡。支付、开卡、UNKNOWN 和人工处理共用该占用关系，不能因支付报价过期就释放已广播或已付款订单的名额。

报价过期但已受理、付款后账号停用、付款后供应商停用、开卡明确失败等情况分别确定处理策略。建议：报价提交时校验有效期，受理后按快照继续跟踪；签名前停用则停止新出款并处理预留，已广播则继续确认；已付款但不能开卡则进入人工案例。UNKNOWN 未排除实际成功前既不能释放名额重开，也不能退款。额度快照改造还必须移除旧创建接口绕过付款的路径，并在服务端校验付款归属、确认状态、一次性消费及名额关联。

### 14.3 P0：资金账单与首页接口契约

建议补充以下接口，名称为设计建议，尚未实现：

| 接口 | 最少返回内容 |
| --- | --- |
| `GET /api/v1/user/wallet/summary` | 钱包就绪/失败/暂停状态，环境和网络，各资产账面/冻结/可用余额、待确认金额、同步时间/高度、出款可用性及原因 |
| `GET /api/v1/user/wallet/deposit-address` | 地址、网络、合约、精度、充币提示与可用状态；未就绪时不能返回临时公共收款地址 |
| `GET /api/v1/user/wallet/bills` | 用户资金账单、分页、类型和状态筛选；测试订单与卡消费均不混入 |
| `POST /api/v1/user/withdrawal-quotes`、`POST /api/v1/user/withdrawals` | 到账/扣款金额、费用资产与承担方、报价过期时间、二次验证绑定、幂等键；另提供本人操作结果查询 |
| `POST /api/v1/user/card-payment-quotes`、`POST /api/v1/user/card-payment-orders` | D/F/O 明细、链费、总扣款、USD 限额、报价期限与名额预留；另提供付款和开卡分别查询 |

首页首期只列 USDT，不引入未经定义的“今日收益”或涨跌幅。只有 USDT 一种支持资产时可显示该资产余额；多资产估值另行定义报价来源、时间及失效规则。资产 API 未接入、请求失败和真实零余额是三个不同状态。金额继续使用最小单位十进制字符串，前端按资产精度格式化，不用 JavaScript Number 累加资金。

账单属于业务操作投影，账本分录属于记账依据，链事件属于链上事实。一次提币可以包含冻结、费用和结算分录，但列表显示一条业务账单；详情可追溯相关分录、网络、资产、方向、金额、费用、交易哈希、状态、时间、业务编号及失败原因。退款和冲正使用新账单关联原单，不能修改原账单冒充成功。签名/广播中的任务应显示处理中，不能因尚未产生结算分录而从用户视图消失。

卡片 `ALL_TIME` 限额是累计消费控制，不是余额。本轮 Nile 原型不展示未经数据支持的“卡内余额”“剩余额度”或消费账单；消费明细页面可后续实施，但生产付费卡运营前须按第 2、8.3、11.2 节完成供应商授权、清算、退款及资金覆盖对账。

### 14.4 P0：把账本不变量和异常处理落成规格

v0.6 已在第 5.1～5.2 节列出资金责任矩阵及事务不变量；P0 按第 11.1 节细化逐项借贷分录，包括外部入账、预留/成功/失败、链费、B→C 待履约、平台资源垫付和人工退款。开发和验收引用同一版本，不能只有科目名称而没有失败/冲突处理。

对账必须比较同一已确认区块高度的链上资金和账本对应余额，不能直接将实时 RPC 余额与扫描旧高度的账本比较。按第 6.1～6.6 节落实完整类型覆盖、性能/滞后、节点可信性、暂停/恢复与告警；历史状态能力和差异精度在 P0 验证定稿。用户自充 TRX 与平台垫付 TRX 的归属、扣费和可提规则按第 9.1 节明确，不能仅打标签。

人工处理不应等于管理员可以任意改状态。需要案例状态、证据、原因、执行者、操作幂等、处理历史；核查、退款授权、资金执行分别限权。退款要预留来源资金、关联原订单并设置累计退款上限，防止重复退。独立签名服务应校验不可篡改/可复核的授权内容及一次性操作标识；仅相信业务进程提交的“已授权”布尔值不能构成隔离。

### 14.5 P1：钱包创建、执行租约和替换细节

- 钱包创建跨业务库与密钥服务，需要稳定创建请求 ID、幂等查询和失败恢复。密钥已生成但业务库写入失败时应找回原地址，不能重试生成另一个钱包；在确认备份与扫描边界前不展示地址。
- 第 7 节“同一钱包串行”还应规定租约到期和旧 worker 恢复的处理。持久化尝试版本与执行令牌，防止过期 worker 再签/覆盖新状态；签名、广播和恢复始终关联同一操作与交易。已有任务租约可以复用模式，但租约本身不保证资金操作只执行一次。
- 保留已确定的 B→C 真实链上转账；补充其每笔资源费、等待确认延迟与交易量预算。它不能按“内部划账几乎零成本”估算。首期无需同时引入其他链实现、多资产估值或微服务拆分。
- 替换 Epusdt 按第 10.2 节提前停止旧受理/任务，完成未决测试单核对与备份，再迁移和启动新扫描；P5 进行最终清理。旧测试资金不因删表成为新系统可提余额；保留核验凭据，资金操作暂停与前向修复不能用重启旧收款替代。

### 14.6 建议补入阶段验收

按第 11 节依赖准入执行：P0 起草规格并优先固化对应模块条件；P1/P2 完成托管、签名基础、扫描与账本及新充币入口；P3 验收统一转账、二次验证、费用与核查操作；P4 接入付费开卡、履约和管理端退款闭环；P5 最终清理旧依赖并完成恢复和持续验收。旧受理/任务在新扫描启用前停用。消费账单页面、礼品券和邀请不作为 Nile 闭环依赖，生产卡服务的资金对账按独立准入要求完成。

新增验收：同用户两笔开卡付款并发只能占用一个有效名额；收款前阻止无资格申请；同一付款不能被旧接口重复消费；报价超时与链上结果未知不误退款；退款不超过原付款可退金额；首页刷新/重登后冻结与处理中账单一致；其他用户无法读取账单或操作；密钥创建成功而业务写入失败可恢复原地址；租约到期旧 worker 复活不重复出款；测试收款成功不伪造用户余额；卡片限额不被展示为余额。
